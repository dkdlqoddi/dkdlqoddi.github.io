## 요청 배경

사용자는 "DX vs AX 자동화" 발표자료의 완성도를 높이고 싶어 합니다.
이 자료는 파이썬 자동화가 디지털 전환(DX) 방식에서 AI 전환(AX) 방식으로 바뀌는 흐름을 설명하는 발표 슬라이드입니다.
디자인 통일, 내용 검증, 시각자료 강화, 설명 순서 개선, 화면 전환 효과(애니메이션) 개선까지 다섯 가지를 한 번에 요청했습니다.

## Unknowns 4분면

|---|---|
| Known Knowns (명시된 요구사항) | 대상은 dx-vs-ax-automation 발표자료. 개선 축은 5가지: 디자인 통일성, 내용 정확성, 텍스트 최소화·시각자료 최대화, 청중 이해 중심 구조, 페이지별 디자인·애니메이션 완성도. 공통 디자인 수정 허용(사용자 원문: "필요하다면, 공통 디자인을 수정해주세요"). |

## 확정 요구사항

1. **슬라이드 순서: 설계 단계에서 새 순서안 1개를 제시하고, 설계 문서 검토 시점에 사용자 승인을 받아 적용한다.**
   근거: 인터뷰 답변 "전체 순서 재검토 허용".
   현재 덱의 배열(subprocess, HTTP, OpenAI SDK, Langchain)은 선행 리뷰 명세가 정한 난이도순입니다.
   이 배열도 재검토 대상에 포함됩니다.
2. **발표용 중심으로 텍스트를 줄인다. 코드 블록은 삭제하지 않고 축약해 유지한다.**
   근거: 인터뷰 답변 "발표용 중심".
   화면당 핵심 메시지 1개를 원칙으로 하고, 산문 문장은 키워드와 다이어그램으로 대체합니다.
   코드 블록 4개는 각각 12줄 이하로 축약하되 슬라이드에 남깁니다.
   기존 코드 복사 버튼(slides/shared/code-copy.js)은 축약 후에도 동작해야 합니다.
3. **공통 디자인을 slides/shared/deck-base.css 한 파일로 추출하고, 5개 덱 전부가 이 파일을 쓰도록 고친다.**
   근거: 인터뷰에서 사용자가 고른 선택지 원문 — "slides/shared/deck-base.css를 새로 만들고 5개 덱 전부를 이에 맞게 고칩니다".
   대상 덱 슬러그 5개: sample, dx-vs-ax-automation, design-ax-transition, integrated-architecture, ai-agent-skills-philosophy.
   추출 대상 블록: 색상 변수(팔레트 토큰), 화면 모서리 장식(HUD), 은하 배경 캔버스 규칙, 제목 폰트 규칙, 표지 강조 효과(글로우), 화면 넘침 방지 규칙(EVA VIEW), 인쇄 방어 블록, 동작 축소(prefers-reduced-motion) 방어 블록.
   각 덱만의 고유 스타일은 그 덱의 HTML 안에 남깁니다.
   공유 파일 참조는 반드시 상대 경로(../shared/deck-base.css)로 합니다. 절대 경로는 인터넷 없이 파일로 열 때 깨집니다.
   장식 HTML 요소(HUD, 은하 캔버스)가 없는 덱에는 해당 규칙이 영향을 주지 않도록 작성합니다.
   ai-agent-skills-philosophy 덱을 공통 디자인에 맞추는 수준은 설계 단계에서 사용자 승인으로 정합니다. 이 덱은 제목 대문자 강제 변환이라는 규칙 위반을 현재 안고 있어, "화면 불변"과 "규칙 준수"가 양립하지 않기 때문입니다.
4. **파손된 sample 템플릿을 수리한다.**
   근거: 사용자 원문 "필요하다면, 공통 디자인을 수정해주세요". sample은 공통 디자인의 정본 템플릿입니다.
   수리 대상 3건 (파일: slides/sample/index.html):
   - 98행 부근: 소속 없는 회전 애니메이션 조각(`to { rotate: 360deg; } }`)이 남아 있음. 삭제합니다.
   - 136~142행: 동작 축소 블록 안에 정지 규칙 대신 배치 규칙이 잘못 들어가 있음. 은하 배경을 실제로 멈추는 규칙으로 교체합니다.
   - 157~158행: 인쇄 규칙 블록이 선택자만 남긴 채 조기 종료됨. 수리 후에는 인쇄 시 별·우주선·은하 장식이 다시 숨겨져야 합니다.
5. **dx 덱에서 확인된 사실 오류 2건을 정정한다.**
   근거: 사전 코드 조사에서 확인된 자기모순.
   | 위치 | 현재 문구 | 수정 방향 |
   |---|---|---|
   | 비교표 슬라이드, HTTP 방법 행 | 없음 (순수 Python) | requests 패키지 필요로 정정 (같은 덱의 설치 주석 `pip install requests`와 모순) |
   | 방법 1 제목 vs 비교표 | 제목 "난이도 하" vs 표 "최하" | 하나의 난이도 척도로 통일. 척도 확정은 설계 단계에서. |
6. **opencode 도구 관련 서술은 외부 검증 후 조건부로 정정한다.**
   근거: 사전 조사에서 의심 2건 식별 — 설치 명령(`pip install opencode`)과 실행 옵션(`--headless -p`)이 실제 도구 규격과 다를 가능성.
   다음 단계(blindspot-pass)의 외부 조사 결과에 따라 정정 여부와 문구를 정합니다.
7. **애니메이션은 이 저장소의 두 가지 표준 관용구만 쓴다.**
   근거: CLAUDE.md의 덱 작성 규칙과 sample 템플릿의 실제 구현.
   관용구 1 — 단계 공개(fragment): 한 화면 안에서 요소를 순서대로 등장시키는 기능입니다.
   관용구 2 — 짝 슬라이드 전환(auto-animate): 연속한 두 슬라이드에서 같은 이름표(data-id)를 단 요소를 부드럽게 이동시키는 기능입니다.
   두 관용구 모두 인쇄 환경과 동작 축소 설정에서는 안전하게 꺼져야 합니다.
8. **파손된 integrated-architecture 덱을 전체 수리한다.**
   근거: 인터뷰 답변 "전체 수리 포함".
   수리 범위: 공유 CSS 교체, 깨진 한글 복구, HTML 구조 오류 수정.
   복구 방법 정정: 조사 결과 깨진 문장은 깨진 채로 추가되어 저장 기록에 원본이 없습니다. 글자 역변환과 문맥 재구성으로 복원합니다.
9. **저장소 설명 문서(CLAUDE.md, README)에 공유 자산 구조를 반영한다.**
   근거: 새 공유 CSS 파일 추가로 기존 문서의 구조 설명이 낡게 됨. 부수 작업으로 자체 결정.

## 미해결 질문

- 가장 복잡한 AX 흐름 다이어그램 슬라이드를 두 장으로 나눌지 — 설계 단계(explainer)에서 새 순서안과 함께 결정합니다.
- 난이도 척도의 최종 표기(예: 하/중/상 3단계 vs 최하/하/중/상 4단계) — 설계 단계에서 새 슬라이드 구성에 맞춰 결정합니다.
