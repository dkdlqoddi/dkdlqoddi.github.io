# philosophy 덱 리뷰 + 하네스(harness) 결과물 폭 시각화 설계 문서

- 날짜: 2026-08-20
- 입력: `docs/blindspot/2026-08-19-philosophy-harness-viz-requirements.md`, `docs/blindspot/2026-08-20-philosophy-harness-viz-unknowns.md`

## 목적과 배경

이 발표 자료(덱)는 인공지능 코딩 도구와 스킬(정해진 작업 절차 묶음) 10가지를 한 장에 하나씩 소개합니다.
아래에서 "덱"은 이 발표 자료 전체를, "모델"은 인공지능 언어모델을 뜻합니다.
자료 곳곳에 "하네스(harness)"라는 단어가 설명 없이 나옵니다.
하네스는 원래 말에 채우는 마구(馬具)를 뜻합니다.
인공지능 분야에서는 "모델을 감싸는 운영 장치 전부"를 하네스라고 부릅니다.
쉬운 비유: 똑똑한 신입사원이 모델이라면, 하네스는 그가 일하는 회사의 매뉴얼·권한·검토 절차입니다.

이 단어가 낯선 청중은 뒤따르는 10개 도구 설명을 따라가기 어렵습니다.
그래서 표지 바로 다음에 개념 설명 슬라이드 2장을 새로 넣습니다.
첫째 장은 하네스가 없을 때 결과물의 폭이 얼마나 넓은지 보여줍니다.
둘째 장은 하네스를 적용하면 그 폭이 어떻게 조여지는지 보여줍니다.
두 장 사이는 그림이 부드럽게 변하는 자동 모핑(auto-animate)으로 잇습니다.

이번 작업에는 전체 리뷰에서 찾은 결함 수정도 포함됩니다.
결함은 세 가지입니다: 인쇄 시 색이 살아나지 않는 문제, 슬라이드끼리 화살촉 정의를 몰래 공유하는 문제, 낭독기용 그림 설명이 없는 문제.
추가로 마무리 장이 없는 점도 이번에 고칩니다.
완성되면 슬라이드는 11장에서 14장이 됩니다.

## 검토한 대안과 트레이드오프

| 결정 | 채택안 | 기각안 | 기각 이유 |
|---|---|---|---|
| 층 개수 | 4층 (검증 루프 포함) | 3층 유지 + 검증형 예시로 보완 | 검증이 가장 중요한 층인데 층으로 안 보이면 "지시문만 잘 쓰면 된다"로 오독됨. 사용자가 4층을 직접 선택 |
| 표현 기법 | 두 장 자동 모핑 | 한 장 단계 공개 / 정지 도식 2컷 | 인터뷰에서 사용자가 모핑을 선택. 폭이 "줄어드는 과정"이 눈에 보임 |
| 폭 그리기 | 밴드 높이가 줄어드는 단순한 부채꼴 | 계단식 깔때기 (층마다 턱이 지는 모양) | 모핑 엔진은 도형을 늘리고 줄이는 것만 하므로, 복잡한 모양은 변신 과정이 어색해짐 |
| 밴드 경계 | 가장자리가 흐려지는 처리 | 또렷한 실선 테두리 | 실선은 "경계 밖은 절대 안 나온다"는 오해를 유발한다는 연구 결과 (unknowns 12) |
| 점의 움직임 | 점들이 자리를 옮겨 모여듦 | 밴드 면적만 줄어듦 | 점이 안 움직이면 "왜 폭이 넓은가(실행마다 다름)"가 전달되지 않음 |
| 예시 스킬 | fablize | ponytail (원래 후보) | fablize는 덱이 이미 "검증 하네스"로 부르는 스킬이라 새 4층과 용어가 이어짐 |
| 화살촉 수정 | 다각형으로 전면 교체 | 화살촉 정의를 그림마다 복제 | 복제는 옛 방식이 남아 정본 규약과 계속 어긋남. 교체가 의존을 근본 제거 |
| 색 수정 범위 | 색 이름표 교체만 (모양·배치 유지) | 10장 전면 재설계 | 사용자가 인터뷰에서 "전면 정규화"를 선택하지 않음 |
| 주소 밀림 | 수용 | 장마다 이름(id) 부여 | 이름 부여도 기존 번호 주소를 한 번은 깨뜨림. 한 번 공개하면 바꾸기 어려운 약속(공개 계약)이 새로 생김. 사용자가 수용을 선택 |
| 과거 문서 | 동결 | 옛 문서의 장 번호 일괄 수정 | 과거 문서는 당시 기록임. 최신 순서는 이 문서가 담당 (아래 "완성 후 슬라이드 순서") |

## 동작 방식

### 새 슬라이드 A: "같은 요청, 벌어지는 결과" (2번 자리)

화면 왼쪽에 "같은 요청"이라고 적힌 상자가 하나 있습니다.
상자에서 오른쪽으로 부채꼴 모양의 밴드가 넓게 퍼집니다.
밴드는 진짜 테두리 선 없이, 가장자리로 갈수록 흐려집니다.
밴드 안에 밝은 점 12개가 위아래로 흩어져 있습니다.
점 하나는 "같은 요청을 한 번 실행해서 나온 결과 하나"를 뜻합니다.
밴드 위쪽 끝에는 "잘된 결과"라는 라벨이 있습니다.
밴드 아래쪽 끝에는 "망한 결과"라는 라벨이 있습니다.
오른쪽 끝에는 밴드 전체 높이를 가리키는 괄호와 "결과물의 폭"이라는 라벨이 있습니다.
그림 아래 본문에 짧은 설명이 한 줄 들어갑니다: 폭이 넓어서 대박과 낭패가 함께 들어 있다는 내용입니다.

### 새 슬라이드 B: "하네스가 폭을 조인다" (3번 자리)

발표자가 다음 장으로 넘기면 그림이 부드럽게 변합니다.
왼쪽 "같은 요청" 상자는 그대로 있습니다.
부채꼴 밴드는 높이가 크게 줄어 가운데로 조여집니다.
점 12개의 최종 배치는 셋으로 나뉩니다.
9개는 좁아진 밴드 안으로 이동해 모입니다.
2개는 밴드 밖에 그대로 남습니다. 하네스가 결과를 완전히 고정하지 못한다는 뜻입니다.
나머지 1개는 검증 루프에 걸려 왼쪽으로 되돌아가는 중입니다.
원래의 넓은 폭은 점선 윤곽으로 남겨 "하네스 없을 때"라고 표시합니다.

조여진 밴드 주위에 하네스 4층이 등장합니다. 층마다 그리는 방식이 다릅니다.
- 지시문(시스템 프롬프트): 위에서 밴드를 지그시 미는 점선 쐐기. 어길 수도 있는 부드러운 제약이라 점선입니다.
- 작업 절차(스킬): 아래에서 미는 점선 쐐기. 같은 이유로 점선입니다.
- 도구 제한: 밴드 위아래를 딱 자르는 실선 막대. 물리적으로 못 넘는 단단한 제약이라 실선입니다.
- 검증 루프: 오른쪽 끝의 문(게이트). 되돌아가는 점 1개에서 왼쪽으로 향하는 화살표가 나옵니다. 어긋난 결과는 반려되어 다시 실행된다는 뜻입니다.

검증 루프 문 옆에 작은 글씨로 실제 예시를 답니다: "실제 예: fablize — 증거 없으면 반려 (뒤에서 소개)".
그림 아래 본문에는 세 줄이 들어갑니다.
첫 줄은 하네스의 정의입니다: 모델을 감싸 힘의 방향을 잡는 운영 장치.
같은 줄 끝에 짧은 비유를 덧붙입니다: 신입사원에게 회사 업무 환경을 갖춰 주는 것.
둘째 줄은 정확한 효과입니다: 결과를 하나로 고정하는 게 아니라, 원하는 결과가 더 자주 나오게 폭을 조인다.
셋째 줄은 경고입니다: 탐색이 필요한 작업에서는 일부러 폭을 넓게 둔다.

### 모핑이 성립하는 조건

두 장의 그림은 같은 좌표계(가로 900 기준)로 그립니다.
움직여야 하는 도형(상자, 밴드, 점 12개)에는 두 장에서 같은 짝 표시를 붙입니다.
일반 규칙: 글자가 든 상자는 크기를 절대 바꾸지 않습니다. 크기를 바꾸면 글자가 찌그러지기 때문입니다.
"같은 요청" 상자는 자리도 크기도 그대로 둡니다.
높이가 변하는 것은 글자가 없는 밴드 도형 하나뿐입니다.
둘째 장에만 있는 요소(4층, 점선 윤곽, 예시 문구)는 서서히 나타나는 대신 즉시 나타나게 설정합니다.
두 장의 제목은 다르게 지어, 목록 화면(조망 모드)에서도 서로 구분되게 합니다.

### 환경별 안전 장치 (이미 갖춰진 것 확인)

동작 축소 설정을 켠 관람자에게는 모핑이 생략되고 두 장이 각각 완성된 상태로 보입니다.
둘째 장은 처음부터 모든 요소가 그려져 있어 애니메이션 없이도 완결됩니다.
인쇄하면 두 장이 각각 한 쪽씩 온전히 나옵니다.
종이 인쇄에서는 공통 규칙이 그림 색을 검정으로 되돌립니다. 이 되돌림은 이번 색 수정(결정 9) 이후에만 동작합니다.

### 결함 수정 방식

첫째, 색 수정입니다. 도형에 직접 적힌 색 45곳을 지우고, 글자색을 따라가는 방식으로 바꿉니다.
그 위에 공통 색 이름표를 붙입니다: 청록은 강조(accent), 회색은 흐림(dim), 빨강은 위험(danger)입니다.
청록과 회색은 값이 완전히 같아 화면 변화가 없습니다.
빨강만 어두운 벽돌색에서 밝은 산호색으로 바뀝니다. 어두운 배경에서 글자가 더 잘 읽히게 되는 의도된 변화입니다.

둘째, 화살촉 수정입니다. 지금은 화살촉 모양 정의가 oh-my-opencode 장(지금 7번, 완성 후 9번) 그림 안에 한 번만 있습니다.
화살표 참조 15곳이 그 정의를 가져다 씁니다. 그중 14곳은 다른 장에 있습니다.
참조 한 곳이 여러 화살표를 한꺼번에 묶은 경우가 있어, 실제 화살촉은 32개입니다.
이 참조를 전부 없애고, 화살표마다 작은 다각형 화살촉을 직접 그립니다.
부수 효과 두 가지가 함께 고쳐집니다.
하나, 빨강·청록 화살표의 촉이 지금은 회색인데 앞으로는 선 색을 따릅니다.
둘, blindspot-flow 장의 "구현 루프(Implementation Loop)" 화살표는 촉 방향이 뒤집혀 있는데, 목적지를 향하게 고칩니다.

셋째, 그림 설명 추가입니다. 이 항목만 신규 2장을 포함합니다. 그림 12개(기존 10장 + 신규 2장) 앞에 각각 눈에 보이지 않는 설명 문단을 넣습니다.
화면에는 안 보이지만 낭독기가 그림의 내용을 읽어 줄 수 있게 됩니다.

부수 정리로, 아무 데서도 쓰지 않는 스타일 규칙 2개를 지웁니다.

### 마무리 장 (14번 자리)

"끝." 한 마디와 발표 기록 목록으로 돌아가는 링크를 담습니다.
마무리 장은 다른 덱 4개 모두에 있습니다. 그중 3개가 쓰는 "끝. + 돌아가기 링크" 형식을 그대로 따릅니다.

### 완성 후 슬라이드 순서 (총 14장)

1. 표지 / 2. 같은 요청, 벌어지는 결과 / 3. 하네스가 폭을 조인다 / 4. ponytail / 5. fablize / 6. grill-me / 7. blindspot-flow / 8. superpower / 9. oh-my-opencode / 10. LangChain Data Agent / 11. Aider / 12. Copilot Workspace / 13. Devin / 14. 끝.

### 병합 전 확인 목록

- 옛 화살촉 방식의 흔적이 0건인지 (참조와 정의 모두)
- 직접 지정한 색이 0건인지
- 그림 수와 그림 설명 수가 같은지 (각 12)
- 슬라이드가 14장인지
- 덱 목록 파일이 규칙에 맞는 형식인지
- 브라우저로 전체를 넘겨 보며 눈으로 확인 (모핑, 목록 화면, 인쇄 미리보기 포함)

## 의도적 범위 제외

- 기존 10장의 그림 글자 크기 상향. 지금 글자는 기준의 절반 크기입니다. 그러나 키우면 10장 전부 배치를 다시 잡아야 해서 다음 사이클로 미룹니다.
- 기존 10장의 그림 좌표계 통일(700을 900으로). 전면 재작업이라 이번 범위를 넘습니다.
- 과거 문서·퀴즈에 남은 옛 장 번호 수정. 과거 기록은 동결하고, 최신 순서는 이 문서가 담습니다.
- 장마다 이름 주소(id) 부여. 사용자가 번호 주소 밀림 수용을 선택했습니다.
- 덱 공통 디자인 파일(deck-base.css) 수정. 필요한 규칙이 전부 이미 있어 손댈 이유가 없습니다.
