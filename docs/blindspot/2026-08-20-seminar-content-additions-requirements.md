# 세미나 덱 콘텐츠 3종 추가 요구사항

## 요청 배경

이 저장소는 발표 자료 모음 사이트다. 발표 자료 두 개가 연작으로 묶여 있다. 1부(`dx-vs-ax-automation`)는 사내 LLM에 연결하는 여섯 가지 방법을 다룬다. 1부에는 개발 과정의 진화와 긴 꼬리 효과 이야기도 함께 들어 있다. 2부(`ai-agent-skills-philosophy`)는 작업 방법론(스킬) 다섯 개를 다룬다. 2부에는 제품 다섯 개 소개와 자율성 스펙트럼 이야기도 함께 들어 있다.

사용자는 두 발표 자료에 세 가지 내용을 추가하고 싶어 한다. 첫째, opencode라는 AI 도구가 LLM API를 호출하고 응답을 받는 과정의 쉬운 설명이다. LLM API는 대형 언어 모델을 프로그램에서 불러 쓰는 접점을 말한다. 둘째, blindspot(맹점)과 unknown unknowns(모른다는 것조차 모르는 영역) 개념의 간략한 설명이다. 셋째, 각 방법론이 망한 결과물과 잘된 결과물의 어느 부분에 영향을 주는지 보여주는 그림이다.

여기서 결과물이란 에이전트에게 작업 하나를 맡겼을 때 나오는 산출물 한 건이다. 코드 변경과 그에 딸린 문서·검증 기록을 묶어 가리킨다.

## Unknowns 4분면

| 분면 | 항목 |
|---|---|
| Known Knowns (명시된 요구사항) | 추가할 내용은 세 가지다. 설명 수준은 "간략하게"다. HTTP(웹에서 쓰는 요청·응답 규약) 설명은 "사용자 입장에서"라는 제한이 있다. 셋째 항목은 글이 아니라 시각 표현이어야 한다. |
| Known Unknowns (답이 필요한 질문) | 시각화의 형태, HTTP 설명의 위치, 개념 설명의 위치. 세 가지 모두 인터뷰로 해소했다(인터뷰 기록 참고). 남은 질문은 미해결 질문 절에 있다. |
| Unknown Unknowns (미지 영역 — blindspot-pass 대상) | opencode가 LLM API에 보내는 요청의 사실관계. 해부도에 넣을 부위 항목의 확정 문구. 새 장 삽입이 건드리는 문서·문구의 전체 목록. "호출 주체 일반" 서술의 예외 유무. |
| Unknown Knowns (인터뷰로 드러난 암묵적 선호) | 새 슬라이드 수를 최소화하려는 선호가 있다(개념 설명에서 새 장 대신 기존 장 보강을 선택했다). 기존 그림 문법과 발표 흐름을 존중하는 선호가 있다. |

## 확정 요구사항

1. **1부에 HTTP 공통 전제 장 1개 추가.**
   - 위치: "6가지 방법 로드맵" 장과 방법 1 장 사이에 넣는다.
   - 내용: 호출하는 쪽이 LLM API에 HTTP 요청을 보내고 응답을 받아 오는 왕복 원리를 그림으로 보여준다.
   - 호출하는 쪽은 사용자 코드일 수도 있고, opencode 같은 AI 도구일 수도 있다. 그래서 이 장은 여섯 방법 전체의 전제가 된다.
   - 예시는 opencode 하나만 쓴다.
   - 사람이 도구에 명령을 입력하는 단계는 왕복 그림의 출발점으로만 표시한다. 이 단계는 터미널 입력이지 HTTP가 아니다.
   - 방법 5·6이 다루는 "사용자에서 opencode serve까지" 구간과 섞지 않는다. opencode serve는 opencode를 서버로 띄우는 방식이다.
   - 역할 경계: 새 장은 원리 그림만 담고 코드 블록을 넣지 않는다. 직접 호출 코드는 방법 1 장이 계속 담당한다.
   - 근거 답변: "방법 1 앞, 공통 전제".
2. **2부의 blindspot-flow 구조 장 보강.** 덱 주석 기준 8장이고, 발표 대본 기준으로는 2부 11장이다.
   - 새 장을 만들지 않는다.
   - blindspot(맹점)의 뜻 한 줄과 unknown unknowns의 뜻 한 줄을 이 장의 요약 상자에 넣는다.
   - 그림 라벨(`Unknowns` / `미지 영역`)은 고치지 않는다. 원어 병기는 요약 상자 문장에서 한다.
   - 동작 보기 장(덱 주석 8b장, 대본 2부 12장)은 고치지 않는다.
   - 근거 답변: "새 장 없이 기존 장 보강".
3. **2부에 결과물 해부도 장 1개 추가.**
   - 형태: 망한 결과물과 잘된 결과물을 나란히 놓는다. 결과물의 부위마다 그 부위를 바꾸는 방법론의 작은 이름표(배지)를 붙인다.
   - 배지 후보군: 2부 스킬 구간에 실제로 등장하는 스킬 다섯 개다.
   - 이 중 전체 흐름을 묶는 스킬(blindspot-flow)을 배지로 쓸지 틀로 쓸지만 미해결 질문 1이다.
   - 근거 답변: "결과물 해부도".
4. **기존 그림 규칙 준수.** 새 그림은 아래 기존 관용구를 따른다.
   - 문서 안에 직접 그려 넣는 벡터 그림(인라인 SVG)을 쓴다.
   - 색은 글자색을 물려받는 색 지정 방식(currentColor)의 기존 4단계 체계를 쓴다.
   - 그림 앞에 숨은 설명문(visually-hidden)을 둔다. 화면에는 안 보이고 화면 낭독기에만 읽히는 글이다.
   - 인쇄 시 색 복구 규칙과 동작 축소(reduced motion) 대응 규칙을 지킨다.
5. **배치 제약 준수.**
   - 슬라이드 높이 상한은 두 값이다. 단계 공개(fragment)가 있는 장은 660px, 없는 장은 700px다.
   - 신설 2장은 단계 공개 사용을 전제로 660px 기준으로 잡는다.
   - 2부 도입부의 연속 화면 전환(모프 체인) 사이에는 장을 끼우지 않는다.

## 자체 해소 항목

증거로 결정하고 기록만 남긴 항목이다. 구현 중 문제가 생기면 재검토한다.

1. **해부도의 위치.** 스킬 구간이 끝나는 지점과 "자율성 스펙트럼" 장 사이에 넣는다.
   - 이유 1: 해부도는 스킬 다섯의 효과를 종합하므로 스킬 구간의 마무리가 자연스럽다.
   - 이유 2: 사용자가 도입부에 새 장 추가를 원하지 않는 선호를 보였다.
2. **발표 시간 처리.** 새 장 2개는 각 45초 안팎으로 발표 대본에 넣는다.
   - 현재 장별 합계는 45분 45초로, 기준 45분을 이미 넘긴 상태다. 추가 후 약 47분 15초가 된다.
   - 기존 장의 시간은 줄이지 않는다. 대신 새 장 2개를 약 37분 압축 경로의 첫 항목으로 올린다. 압축 경로는 시간이 부족할 때 건너뛸 장 목록이다.
   - 대본 머리말의 총 시간·덱 장수·유인물 쪽수 숫자를 실제 값으로 갱신한다.
   - 머리말의 "45분 엄수" 안내 문장도 압축 항목 조합을 다시 계산해 고쳐 쓴다.
3. **사실 검증 방식.** 호출하는 쪽에서 LLM API까지 구간의 사실은 공식 문서로 확인한 내용만 적는다.
   - 방법 5·6의 실측값은 "사용자에서 opencode serve까지" 구간의 값이다. 따라서 새 장에 가져다 쓰지 않는다.
   - 검증 사실을 화면 구석에 남기는 기존 각주 관례를 따른다. 새 장은 실측이 아니라 문서 확인이므로, 버전 번호 대신 문서 확인일을 남긴다.
4. **수량 문구의 범위.**
   - 고치지 않는 것: 덱 안의 "여섯 가지"·"다섯" 문구다. 방법과 스킬의 개수가 변하지 않기 때문이다.
   - 고치는 것: 발표 대본 머리말의 덱 장수·유인물 쪽수·시간 합계와 "45분 엄수" 안내 문장이다.
5. **보강 위치의 세부(요구사항 2).** 수정은 요약 상자 안에서만 한다. 그림에는 손대지 않는다. 정의 2줄을 새 항목으로 추가하고, 기존 문장은 중복 병기 한 곳만 다듬는다.

## 미해결 질문

1. 해부도의 부위 항목을 무엇으로 확정할지. 전체 흐름을 묶는 스킬(blindspot-flow)을 배지로 쓸지 틀로 쓸지도 여기에 포함된다. (blindspot-pass 대상)
2. 호출하는 쪽에서 LLM API까지 구간의 사실관계. 요청이 가는 주소의 형태, 요청·응답의 모양, 응답을 조각조각 이어 받는 방식(스트리밍)의 언급 여부, "호출 주체 일반" 서술의 예외 유무. (blindspot-pass 대상)
3. 새 장 삽입이 건드리는 파일·문구 중 아직 목록에 없는 것을 찾는 일. 자체 해소 2·4에서 이미 갱신하기로 결정한 항목은 제외한다. (blindspot-pass 대상)
4. 보강 장과 신설 장이 높이 상한(660px/700px)을 지키는지 여부. (구현 중 실측으로 확인)
