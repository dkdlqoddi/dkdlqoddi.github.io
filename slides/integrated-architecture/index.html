망 연동 환경에서의 3가지 아키텍처 대안

오픈소스 모델 제어를 위한 3가지 방법론

망 분리 환경에서 사내 모델을 활용하여 VWP망의 데이터에 안전하게 접근하기 위한 3가지 아키텍처 방법론을 비교합니다.

방법론 1: Office망 LLM (Harness 통제) + API Server + MCP Server (통제형)
방법론 2: Office망 LLM (Harness 통제) + Office Docker + S3 Server (우회형)
방법론 3: VWP망 LLM (Harness 통제) + VWP Docker (완전 격리형)

방법론 1: MCP Server 기반 통제형

오피스망의 LLM이 Harness에 감싸져 있고, API Server를 거쳐 VWP망의 MCP 서버를 통해 파일 시스템에 접근하는 구조.

장점: API Server와 MCP Server가 위험한 요청을 필터링하고 통제함.

방법론 2: S3 Server 기반 우회형

오피스망의 LLM이 Harness에 감싸져 있고, Docker가 S3를 통해 VWP망의 파일 시스템을 Read-Only로 강력하게 마운트하는 구조.

장점: 물리적으로 VWP망에 대한 실행(Execute) 코드가 넘어가지 않음.

방법론 3: VWP망 내재화 (완전 격리형)

VWP망 내부에 Harness와 LLM, Docker를 모두 배치하여 망을 넘어갈 필요가 없는 구조.

장점: 방화벽을 통과하지 않으므로 망 연동 지연(Latency) 제로.

향후 과제: 성능 및 보안 테스트

성능 측정 (Latency)

망을 거치는 방화벽 검사 및 Agentic Loop 반복에 따른 응답 속도 지연율 비교

보안성 (Isolation)

망 분리 규정 준수 여부 및 실행 코드가 내부망으로 주입될 수 있는 취약점 점검

Issue 1: Hallucination

CodeMate LLM의 치명적 오작동 사례

사내 상용 모델(CodeMate)의 추론 능력 부족으로 인해, 존재하지 않는 툴을 호출하거나 필수 인자(Parameter)를 빼먹는 JSON 오류가 매우 잦습니다.

이로 인해 사용자는 오류 메시지를 반복해서 봐야 하는 불편함을 겪게 되며, Harness의 JSON 파싱(Auto-Retry) 부담이 극도로 가중됩니다.

// 예상되는 올바른 MCP 툴 호출 { "tool": "vwp_search_logs", "args": { "query": "error" } } // 실제 CodeMate가 뱉어내는 할루시네이션 예시 { "tool": "search_db_which_doesnt_exist", "arguments": "error" // Object가 아닌 String 반환 }

VWP망의 로그 파일이나 DB 레코드 쿼리 시, 필터링되지 않은 원본 데이터(Raw Data)가 한 번에 쏟아져 들어옵니다.

이로 인해 LLM의 컨텍스트 윈도우가 즉시 가득 차게 되며, 이전 대화 내용(Memory)마저 지워지는 대형 참사가 발생합니다.

Mitigation & Next Steps

Schema Auto-Retry

Harness 계층에서 엄격하게 JSON을 파싱하고, 잘못된 호출은 LLM에게 즉각 재시도 지시

Payload Compression

API Server단에서 불필요한 로그 필드를 잘라내고 요약하여 컨텍스트 보호

Safe Whitelisting

VWP망의 데이터 손상을 막기 위해 MCP Server에서 Read-only 기능만 노출
