망 연동 환경에서의 2가지 아키텍처 대안

오픈소스 모델 제어를 위한 2가지 방법론

망 분리 환경에서 사내 모델을 활용하여 VWP망의 데이터에 안전하게 접근하기 위한 2가지 아키텍처 방법론을 비교합니다.

방법론 1: Office망 LLM (Harness 통제) + API Server + MCP Server (통제형)
방법론 2: VWP망 LLM (Harness 통제) + VWP Docker (완전 격리형)

방법론 1: MCP Server 기반 통제형

오피스망의 LLM이 Harness에 감싸져 있고, API Server를 거쳐 VWP망의 MCP 서버를 통해 파일 시스템에 접근하는 구조.

장점: API Server와 MCP Server가 위험한 요청을 필터링하고 통제함.

방법론 2: VWP망 내재화 (완전 격리형)

VWP망 내부에 Harness와 LLM, Docker를 모두 배치하여 망을 넘어갈 필요가 없는 구조.

장점: 방화벽을 통과하지 않으므로 망 연동 지연(Latency) 제로.

한눈에 보는 아키텍처 대조

상단은 방법론 1(방화벽 통과형), 하단은 방법론 2(완전 격리형)를 대조하는 통합 다이어그램입니다.

현실적인 제약사항 ①

VWP망 개발 서버 완전 고갈

VWP망 내 가용 개발 서버 5대 중 4대는 GAIA가 점유 중이며, 남은 1대마저 GAIA 2.0과 DLQA Infra 서버 구동으로 과부하 상태입니다. 무거운 Docker를 돌릴 자원이 없습니다.

무거운 가상 OS(Docker)를 띄울 만한 유휴 컴퓨팅 자원이 없습니다.

현실적인 제약사항 ②

사내 LLM API 제한 (100 RPM & Timeout)

에이전트가 오동작을 스스로 복구하기 위해 짧은 시간에 수많은 요청을 보내면, 분당 100회 제한에 도달하여 Timeout이 발생합니다.

지속적인 Auto-Retry Loop는 현재의 100 RPM 제한 환경에서 치명적인 병목(Bottleneck)이 됩니다.

사내 제공 LLM (DS Assistant API) 성능 비교

Gemma4, GLM 5.2, Kimi V3, DeepSeek V4 등 4종의 모델 성능 비교표. 제한적인 컨텍스트 창과 타임아웃 문제를 보여줍니다.

모델명 추론 성능 한글 이해도 컨텍스트 창 응답 속도
Gemma 4 75 점 60 점 8K (매우 부족) 🚀 빠름
GLM 5.2 80 점 85 점 32K 🐢 느림 (Timeout)
Kimi V3 82 점 90 점 128K 🚶 보통
DeepSeek V4 95 점 88 점 64K 🚶 보통

* 코드를 분석하기 위해서는 최소 32K 이상의 Context 창이 필수적이나,
안정적으로 넓은 Context를 지원하는 모델은 응답 지연(Timeout)이 자주 발생합니다.

결론 및 요청사항

개발 서버 추가 구매 (증설) 필요

현재의 한계

  • 무거운 가상화(Docker 샌드박스)를 감당할 VWP 서버 여력 제로
  • LLM 100 RPM 제한으로 인한 파이프라인(Agentic Loop) 마비
  • 대용량 코드를 소화할 수 있는 모델들의 잦은 Timeout

해결 방안

  • 독립적인 VWP망 개발 서버 추가 배치 필수
  • 안정적인 인프라 기반 위에서 2가지 아키텍처 대안을 모두 검증 가능
  • 결과적으로, 인프라 투자가 선행되어야 진정한 '안전한 설계 자동화' 완성

2차 방어: Payload Compression

사내 모델은 처리 가능한 컨텍스트 길이가 짧아 Context Overflow에 취약합니다.

API Server는 망 연동 방화벽을 통과한 원본 데이터를 가로채 핵심 에러만 필터링(Payload Compression)하여 오픈소스 모델에 전달합니다.

3차 방어: 물리적 샌드박스

그림 설명: 보호 대상 디렉토리는 Read-Only(RO)로 연결하고, 작업 대상 디렉토리만 Read-Write(RW)로 연결하여 파일 손상을 물리적으로 차단합니다.

Agentic Loop

끝내 답을 찾아내는 오동작 복구 과정

결론: 안전한 설계 자동화 파이프라인

멍청한 사내 모델도 이 아키텍처 위에서는 안전하고 자동으로 임무를 수행합니다.

Issue 1: Hallucination

CodeMate LLM의 치명적 오작동 사례

사내 적용 모델(CodeMate)는 추론 능력 부족으로 인해, 존재하지 않는 툴을 호출하거나 필수 인자(Parameter)를 빼먹는 JSON 오류가 매우 잦습니다.

이로 인해 사용자는 오류 메시지를 반복해서 봐야 하는 불편함을 겪게 되며, Harness의 JSON 파싱(Auto-Retry) 부담이 극도로 가중됩니다.

// 예상하는 올바른 MCP 툴 호출 { "tool": "vwp_search_logs", "args": { "query": "error" } } // 실제 CodeMate가 뱉어내는 할루시네이션 예시 { "tool": "search_db_which_doesnt_exist", "arguments": "error" // Object가 아닌 String 반환 }

VWP망의 로그 파일이나 DB 레코드 쿼리 시, 필터링되지 않은 원본 데이터(Raw Data)가 한 번에 쏟아져 들어옵니다.

이로 인해 LLM의 컨텍스트 한도량이 즉시 가득 차게 되며, 이전 대화 내용(Memory)마저 지워지는 참사가 발생합니다.

Mitigation & Next Steps

Schema Auto-Retry

Harness 계층에서 엄격하게 JSON을 파싱하고, 잘못된 호출은 LLM에게 즉각 재시도 지시

Payload Compression

API Server단에서 불필요한 로그 필드를 잘라내고 요약하여 컨텍스트 보호

Safe Whitelisting

VWP망의 데이터 손상을 막기 위해 MCP Server에서 Read-only 기능만 호출
